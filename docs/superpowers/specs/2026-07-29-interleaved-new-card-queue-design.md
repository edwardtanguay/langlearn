# Interleaved Top-Rank New Card Queue Algorithm Design Spec

**Date:** 2026-07-29  
**Status:** Approved  
**Topic:** Interleaved 3:1 Top-Ranked New Card Study Queue

---

## 1. Executive Summary
When users import or add a batch of flashcards (e.g. 80 cards), they want to immediately study the top-ranked new cards while they are fresh in mind, without completely drowning out active review cards that are already due. 

This design introduces a **3:1 Interleaved Top-Rank Queue Algorithm** that limits new cards in a session to the top 30 highest-ranked unreviewed cards, interleaved at a 3:1 ratio with due review cards.

---

## 2. Goals & Success Criteria
* **Freshness & Momentum:** Top-ranked new cards (where `nextTestTime == null`) surface immediately after creation.
* **Balanced Review:** Existing active cards (`nextTestTime <= NOW()`) are kept in rotation so spaced repetition is not neglected.
* **Controlled Batching:** Prevent overwhelming sessions when adding large batches of cards (e.g., 80+), capping the new card pool at the top 30 ranked cards per session queue request.

---

## 3. Queue Construction Algorithm

### 3.1 Card Pools
1. **New Cards Pool (`poolNew`)**:
   - Condition: `status == 'LEARNING'` AND `nextTestTime == null`.
   - Ordering: `rank DESC`, `id ASC`.
   - Cap: Top $N_{new} = 30$ cards.

2. **Due Cards Pool (`poolDue`)**:
   - Condition: `status == 'LEARNING'` AND `nextTestTime <= NOW()`.
   - Ordering: `rank DESC`, `id ASC`.
   - Cap: Top $N_{due} = 10$ cards (matching the 3:1 target ratio for a 40-card max batch).

### 3.2 Interleaving Ratio & Sequence
The queue is generated by pulling cards from `poolNew` and `poolDue` in a repeating **3 New : 1 Due** pattern:

$$\text{Queue} = [N_1, N_2, N_3, D_1, N_4, N_5, N_6, D_2, \dots]$$

#### Fallback Rules:
* If `poolDue` is exhausted or empty, remaining slots are populated by `poolNew`.
* If `poolNew` is exhausted or empty, remaining slots are populated by `poolDue`.

---

## 4. Architecture & Implementation

### 4.1 Server Utility Function (`server/utils/algorithm.ts`)
Add `buildInterleavedQueue<T>(newCards: T[], dueCards: T[], options?: { newRatio?: number; dueRatio?: number }): T[]`:
* Pure utility function that takes two arrays of cards.
* Interleaves them according to the specified ratio (default `newRatio: 3, dueRatio: 1`).
* Returns the combined array.

### 4.2 Endpoint Integration (`server/api/flashcards/index.get.ts`)
Update the default active flashcard fetching endpoint:
* Query up to 30 unreviewed cards (`nextTestTime == null`) ordered by `rank DESC`.
* Query up to 10 due cards (`nextTestTime <= NOW()`) ordered by `rank DESC`.
* Run `buildInterleavedQueue(newCards, dueCards)` and return the ordered array.
* If `allFilter` or specific query overrides are present, retain standard fetching logic.

## 5. Verification Plan

### 5.1 Unit Tests (`test/algorithm.test.ts` or similar unit test)
* Test `buildInterleavedQueue` with:
  1. Equal counts of new and due cards (e.g. 10 new, 10 due) -> Verify 3:1 pattern.
  2. 0 due cards -> Verify fallback to 100% new cards.
  3. 0 new cards -> Verify fallback to 100% due cards.
  4. Non-multiples of 3 (e.g. 5 new, 2 due) -> Verify full consumption without dropping cards.

### 5.2 Integration Verification
* Create sample cards (80 new, 10 due) and hit `GET /api/flashcards`.
* Verify that returned items start with top 3 ranked new cards, followed by 1 due card, and total count respects the configured caps.
